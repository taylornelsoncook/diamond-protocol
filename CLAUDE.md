# Diamond Protocol: project guide for Claude Code

## The business
Diamond Protocol ("Built Under Pressure") is a mobile sports-performance coaching business. It trains at its own facility, at clients' homes and in parks. Most clients are **parents paying for youth athletes**. Revenue mix: about 30% private training, 50% group classes, 20% other (camps and clinics, team contracts with schools and clubs billed a flat monthly fee, online programs, evaluations). The owner is not a developer: explain things in plain language and keep them informed of anything they need to do themselves.

## What this is
One web platform plus an iPhone app:
- **Coach dashboard** (`/`): Today, Schedule and rosters, Point of sale, Clients, Teams (school contracts and invoices), Testing, Billing, Programs, API & integrations, Settings (exercise library for all staff; staff, security, backups and jobs, data requests and the activity report for the owner; old `#/staff` links land there).
- **Parent portal** (`/parent`), **family sign-up** (`/join`), **ask about training** (`/start`), **Book now page** (`/book`, embeddable with `/embed.js`; the only page other sites may frame), **terms and privacy** (`/terms`, `/privacy`), **athlete workout app** (`/app?token=`), **online store** (`/shop`), **printable progress report** (`/report.html`), **school invoice page** (`/invoice/:token`), **pay link page** (`/pay/:token`), **open-spot offer page** (`/spot/:token`), **self check-in** (`/here/:code` from the door poster `/poster.html`, tablet `/kiosk`), **weight-room screen** (`/tv`), **course certificate** (`/certificate#token`), **coach's education** (`/learn`, public).
- **Open API** (`/v1/...`, reference at `/v1/openapi.json`) and a parent API (`/portal/api/...`).
- **iPhone app** `ios/` (SwiftUI "DP Coach": Today/rosters, Charge with Tap to Pay, Testing stopwatch, Clients). **Written but never compiled**: the first build on a Mac may need Swift fixes. `test/ios-contract.test.js` pins every field it reads.

Read `README.md` for features, `CHECKLIST.md` for the owner's to-do list, `DEPLOY.md` for going live, `ios/README.md` for the app.

## Rules we decided (don't undo these without asking the owner)
- **Athlete ID** (`AVALOP2026`: first 3 of first name + first 3 of last name + year joined, `-2` for duplicates) is permanent and ties all data together. It lives on the client; a roster line's `athlete_id` is only a copy. A team roster line's own ID from before version 37 still finds its client through `athlete_id_aliases` (`athlete-ids.js#findByAthleteId`); new IDs never reuse an alias.
- **One profile per athlete** (owner: "Even if they sign up with a team I want everything going to 1 profile per athlete"): every `team_roster` line has `client_id`. Adding to a roster links a client the coach chose or an exact Athlete ID, otherwise creates a client (name, position, grad year, school for a school team; no family, no membership). Names are never linked on their own (the coach chooses). Results, device links, testing day athletes, walk-ups, queue linking and `team_attendance` (by `client_id`) are always on the client; a `roster_id` from an older integration means that line's client (`clientOfRoster`). `perf_results.roster_id` and `athlete_links.roster_id` stay only for compatibility and are always empty. Team-only athletes (on a roster, no membership) are clients in the "Team only" view, never active clients, and aren't counted as new clients on Today. Archived athletes stay on the roster line but drop out of current rosters, team testing days, team messages and pickers until restored. A client with no family can be put in one (`POST /v1/clients/:id/family`, owner and coach) so parents see them in the portal.
- **Results only land in a profile by Athlete ID, our internal IDs, or a device ID the coach linked by hand. Never guess by name.** Everything else waits in the queue (`results_queue`) for manual linking.
- **Uploads and imports are all or nothing:** check the whole file, list every problem by row and column, save nothing until clean, re-check at save time, save in one transaction. Unusual-but-possible values need explicit confirmation.
- **Roles** (Owner, Coach, Front desk) are enforced server-side in `services/security.js`; coaches and front desk never see money (`hideMoney` removes amounts from what they read, apart from what the counter needs to take a payment). Update the rules there for new endpoints.
- **Possible values:** a metric's range is the coach's own from the Test library (`perf_metrics.min_value/max_value`, both ends) or else the built-in one in `test-library.js` `RANGES` (may be one-sided). `performance.rangeOf` is the one source; typed results, the stopwatch, uploads and device imports all refuse values outside it, and the API returns it as `range: [min, max]` (null for an open end).
- **Parents see test results only after a testing day is shared** (unless the setting says otherwise).
- **Terms/privacy placeholders start with `[`** and are never shown to parents or required.
- Deleting a family removes personal data but keeps payment records without names.
- Every change and sign-in is audit-logged without storing request bodies.
- **Coaches:** `coach_id` (a user, owner or coach, never front desk) on `class_series`, `class_sessions` (a sub overrides one session; handing a class over moves upcoming sessions still on the old coach) and `availability`. Open slots (`schedule.openSlots`, used by `/v1/slots`, the portal and `/book`): hours with a coach are blocked by anything that coach leads anywhere plus sessions at that place with no coach; hours with no coach by anything at that place; a turned-off coach's hours and days in `time_off` (a coach's, or the whole facility's when `user_id` is empty) aren't offered. `bookSlot` saves the session with the coach before charging, so a second booking of that coach at the same time (any place) is refused.
- **Open spots and trial offers** (`services/spots.js`): Today's list is every group class, clinic and camp day sold by the day with a spot left in the next 7 days, for every coach (coaches see it too, without prices; `?coach_id=me` for "My classes only"). The automatic job still only offers group classes and clinics within 30 hours. Trial offers (`/v1/sessions/:id/trial-offer`) are owner only in `security.js`; the price lives on `spot_offers.price_cents` (NULL = standard offer) and only `bookOffer` passes it to `schedule.book` (`offerPriceCents`), so no other booking is affected. A membership that covers the class still covers it; 0 books with coverage `none`. Price: whole cents, 0 to the drop-in (or $200 with none), and never more than the drop-in at booking time if it was lowered since. One booking per trial link, even when two athletes on it book at once; a trial booking never lands on the waitlist (the waitlist books at the usual price).
- **Owners see everything:** nothing on the owner's screens is limited to the signed-in user; per-coach views (`/v1/coach-summary`, owner only; Schedule `?coach=`) are filters the owner chooses.
- **Archived clients** (`clients.archived_at`) are left out of `/v1/clients` (unless `?archived=true|all`), dashboard counts and every job that contacts families (reminder texts, open-spot offers, review asks, announcement emails, at-risk). New lists or jobs that reach clients must leave them out too. Archiving is refused with a membership and cancels upcoming bookings only with `confirm: true`; archived clients can't be booked or given a membership. "Active client" = not archived and membership `active` or `trialing` (`clients.clientCounts`, `status=current`), the same on Today and the client list.
- **New-client duplicate checks** (staff only, never the portal or public sign-up): an email that belongs to a client or a parent login is refused with a link to the record; the same name + birthday (archived too) or a phone on file asks first only with `check_duplicates: true` (the dashboard sends it; API integrations aren't asked). Front desk can't assign a program when adding a client or sibling.
- **Point of sale:** money in whole cents. Discounts are on the whole sale (percent or amount), always with a reason, never the whole sale; owners give any, coaches and front desk up to `staff_discount_max_pct` (owner setting, 0 = owners only, the default: see Discounts below). Undo = a full refund by the person who took the sale, within 10 minutes of it being paid, nothing refunded yet; it shares the `sale:<id>` lock with refunds. `request_id` on `POST /v1/sales` returns the first sale for a repeat press. Takings are midnight to midnight in the business time zone; a refund counts on the day it was made. Coaches see and work only their own sales and never the takings; front desk runs the counter but doesn't refund. Readers charge only at their own location. Receipts go to the family's primary parent (or a typed address); deleting a family clears where receipts went and their links.
- **Billing** is owner only. Membership refunds, voids, payments by hand, charges and Stripe webhooks share the `invoice:<id>` lock; refunds never exceed what was paid and use the new refunded total as Stripe's idempotency key; a card payment is refunded to the card, a cash or check payment only logged. **One retry model** (owner decision): a retry the owner starts (Retry or Retry all) or a parent starts (the portal's Try again, while the payment has had fewer than 8 tries in all, only with a card on file) is manual: it never cancels a membership, leaves the next automatic retry where it was and doesn't count toward the limit. Only automatic tries (the first charge, the scheduled retries, and the charge when a family saves a new card) count in `invoices.auto_attempts` toward `MAX_ATTEMPTS` (5, owner decision: the first charge and 4 retries, one retry after the lockout); `attempts` counts every try and is Stripe's idempotency key (`<invoice>:<attempts>`); every try is in `invoice_charges` with `source` (`automatic`, `new_card`, `owner`, `parent`). A pay link or a payment by hand pays the invoice without touching either counter. All of them go through `billing.attemptCharge` (or `markInvoicePaid`) under the `invoice:<id>` lock.
- **Late card approvals** (owner decision): every membership charge try is written to `invoice_charges` before Stripe is called, with Stripe's PaymentIntent id when it comes back and the try's id in the metadata (`charge_attempt_id`), so a late answer always finds its try, even after a pay link replaced the invoice's `payment_ref` or when the call errored before an id came back (a retry after an error reuses that try's row, key and metadata). A try approved while the invoice is still owed pays it. A try approved after the invoice was paid another way (pay link, cash/check, another try) or voided is refunded automatically, exactly once (under the invoice lock, the try's `late_outcome` checked first, Stripe key `invoice-paid-twice-<invoice>-<ref>`), and the owner gets an email, a Today "needs your attention" item (until Mark handled) and an `invoice.paid_twice` event. It's logged on the try (`late_outcome`, `refund_ref`), not in `invoice_refunds`: the invoice's own payment isn't refunded and money in isn't changed. A refund Stripe refuses is flagged (`refund_failed`) and tried again, same key, on the next event. Card reminders go out at most once a business day per family. Voiding a declined charge brings a membership past due only because of it back to active.
- **Collecting for a booking** is only `booking_id` on a sale (checked: unpaid, not canceled, the sale's client, the sale covers the price; one at a time per booking). A sale's note is only a note.
- **Workout logs** (`workout_logs`) are finished workouts only (streaks, goals and counts read them). The app saves a whole workout at Finish (sets, effort, note) with the phone's `request_id`, so a double tap or an offline resend returns the first save; the phone's `finished_at` counts only within 72 hours. One log per workout per program: logging on the weight-room screen after the app (same business day) links the app's log to the session; finishing in the app after the screen adds the sets to the screen's log. Weights in the app and on the screen come from the same `loadFor` (tested max, readiness drop). Paused, canceled and archived athletes can't log.
- **Parent portal:** every portal route goes through the signed-in parent's family (`portal.athleteOfFamily`, `familyBooking`); archived athletes are hidden from the family. Families can't book an athlete into overlapping sessions (a waitlist spot counts; `schedule.clashText` under the athlete's lock); staff only get a warning. The calendar feed stores only a hash of its secret, shows first names, session names, times and places, and a reset kills the old link. Membership requests never change billing: the owner changes it on the client page and marks the request done or declined (the parent is emailed); one open request per athlete. Parents retry a declined payment while it has had fewer than 8 tries in all (a manual retry like the owner's: it never cancels, doesn't count in `invoices.auto_attempts` and leaves the next automatic retry where it was); removing the card is refused while a membership uses it; the other parents are emailed on card and parent changes.
- **Claiming and merging profiles:** a parent's Athlete ID attaches an existing profile only when it is team-only (on a team roster, no membership, no card of its own), has no family, isn't archived, has fewer than 3 earlier claims that didn't match (`profiles.MAX_MISSES`), and the name and full birthday match; anything else makes a new profile and, if the ID belongs to a profile, files an open `profile_claims` row for the owner. The parent's answer is the same whether or not the ID exists; portal claims are rate-limited (5 an hour per parent, 10 per network). Merging (owner only) moves every row pointing at the other client (found from the database's foreign keys) in one transaction, keeps an alias for the old Athlete ID, and is refused with two memberships, different families, both booked for one session, both holding a spot in one class or two saved cards.
- **Reading reminders** are sent by a coach (Remind, Remind overdue), never automatically: an assignment at most every 12 hours, an athlete at most one reading reminder every 12 hours, never archived or deleted athletes, never addresses in `email_optouts`, and nobody on a team whose contract ended (its reading is never overdue). Assigning is all or nothing: every athlete is checked first; those who already have it (on their own or through a team) are skipped and named. Due dates run from today to a year out.
- **Staff notes** (`client_notes`): coach-only notes never reach front desk (filtered server-side) and never reach a family: owner decision, they're left out of `legal.exportFamily` (the parent's `/portal/api/export` and the owner's `/v1/families/:id/export`, which is what a data request hands over; there is no separate staff export). Other staff notes are in the family export; all are removed on deletion. The export also has the parent portal's data (membership requests, notes to the coach on bookings, the card's expiry, profile claims, signed-in devices); deleting the family removes it.
- **Coach clashes are warnings** (owner decision): giving a coach or sub a session, moving a session, editing a class's coach, time or days, adding a class or one-off session with a coach, and giving a coach hours check that coach's other sessions at overlapping times (any place) and their days off (their own and the facility's). The API answers 409 `coach_conflict` with `details.warnings` until the same request comes with `confirm: true`; the dashboard shows the clashes and "Save anyway". Anyone who may edit the schedule can save anyway; front desk can't edit these. Handing a coach's work over (Staff & security) uses the same check (`schedule.handOverClashes`): 409 `coach_conflict` until `confirm: true` (hand everything over anyway) or `leave_conflicts: true` (leave the clashing sessions with the old coach).
- **Moved sessions** (a single session or through a class edit) email booked families and, owner decision, waitlisted families ("still on the waitlist"), once per family; archived athletes are left out, and a family only on waitlists isn't emailed at an address in `email_optouts`.
- **Deleting a program or workout keeps history** (owner decision): athletes' logs and sets stay (`workout_logs.workout_id`/`assignment_id` become empty, the snapshot columns say what it was), out of the program's numbers but in the athlete's history, the athlete app (a day's details on the Accountability calendar too, under the workout's old title), the client page and the family export. A log of a removed workout can't be reopened.
- **Offline backdating** stays at 72 hours (owner decision: no change): the phone's `finished_at` counts only within 72 hours.
- **Front desk** keeps editing parents, re-sending the sign-in email and recording paper waivers (owner decision: no change).
- **Leads** (owner decision, also for the CRM batch): owners and front desk work every lead; a coach sees and works only the leads the owner gave them (`leads.coach_id`, filtered in `leads.js` for the list, details and updates, a coach can't tell others exist), can't add, delete or reassign leads, and doesn't see lead events in the activity feed or other leads on Today. Only the owner sets `coach_id` (the coach is emailed).
- **CRM** (B15, on the leads decision above): front desk works every lead (notes, calls, one-to-one emails and texts, tasks, converting, putting a family back in the pipeline) but not reports, import, export, templates or group messages (owner only in `security.js`); a coach works only leads given to them (every lead route, the timeline, tasks and a family's contact history go through `leads.leadScope`), adds tasks only for themselves, never looks up families or clients by email or phone (their lead page lists only their own leads as possible duplicates), logs notes and calls on client profiles, and doesn't email, text or re-open families one-to-one. Front desk give tasks to themselves, the owner or front desk, never a coach. A lost lead needs a reason. Converting links a profile staff chose (client id or exact Athlete ID) or creates one through the Clients screen's rules, once per lead, in one transaction; notes become a staff note; text consent doesn't carry over (STOP and email opt-outs do). Emails respect `email_optouts` (staff can add, never remove) and end with a stop link; texts go to a lead only with their OK (and where it came from) on a US mobile that hasn't texted STOP, and to a family only to parents who turned texts on. Imported leads get no automatic emails or texts and start New or Contacted. Payments show on a timeline for the owner only.

- **API keys** have an access level (`read`, `results` = read and send results/device files, `full`), checked on every request in `server.js` (`security.keyAllows`); new keys are read only unless chosen, keys from before version 42 keep full access. Keys never manage keys, webhooks, staff or the outbox (session routes), and only full-access keys get an athlete's app link. - **How a client trains** (`clients.training_type`: `hybrid`, `in_facility`, `remote`, or empty): any staff member who can edit the client picks it; it shows under the name in the client list and on the client page, filters the list (`?training=`, `unset` too) and is in the client export.

A difference invoice is a one-off: a decline never makes the membership past due, never retries on its own, never cancels or locks; the owner or parent retries it. - **Outside data** (`services/dataimport.js`, Settings → Data import, the client page's Recovery & sleep, the portal's Progress tab, the athlete app's Performance tab): owners and coaches bring files in for any athlete, parents for their own athletes (portal routes, also closed while the family is locked out); front desk only sees it. The athlete is always chosen by the person, never found by a name in the file. All or nothing like other imports: a preview lists every problem by row and column and nothing saves until it's clean. WHOOP files are recognized by their columns; a WHOOP day is the date the athlete woke up; naps are left out; a 0 where 0 isn't possible (heart rate, respiratory rate...) means not measured and is left out. Parents undo only their own imports. The PDF and Excel readers stop at size limits (unpacked bytes, font entries, pieces of text) so a hostile file can't tie up the server. Archived athletes are refused. Shown only for now (owner decision): it doesn't change workouts or readiness. In the family export and removed with the family.

Video links must be https and playable (`videoKind`), stills https .jpg/.png/.webp. `exercises.poster_url` shows before a video file plays (`videoEmbed` poster, preload none); a new video link drops the old still unless a new one comes with it. The library shows 60 at a time.
- **Build from a PDF** (`services/workoutimport.js`, owners and coaches, session only; front desk can't): the file (PDF up to 20 MB, or a PNG/JPG/WebP photo up to 5 MB) goes to the Anthropic Messages API by `fetch` (streamed, `claude-opus-5`, adaptive thinking at medium effort, `output_config.format` JSON schema, `fallbacks: "default"` (text before a fallback is dropped); `DP_WORKOUT_MODEL`, `ANTHROPIC_BASE_URL`; tests use `ctx.readWorkoutFile`). Limits: PDFs up to 100 pages, photos up to 3.7 MB (Anthropic's 5 MB counts base64), 20 reads an hour per person and 150 a day for the business; a library over 1,500 exercises isn't listed for Claude (names are matched here). The draft is never saved on its own. Library matches: the same name after abbreviations and plurals (`normName`) is "exact" and starts chosen; Claude's `library_match` or a close name is only "suggested" and starts empty until the coach presses Use it (or Use all); anything else is offered as a new exercise. The page picks exercises from a typed list (a datalist), so a big library stays fast, and "Save it as" is locked while a draft is open; adding to a program starts the file's weeks after its last week. Saving is all or nothing with every problem listed (the builder's rules: week 1-52, day 1-7, a day not already in the program, sets and reps up to 80 characters, a percent of a tested max 30-110, a new exercise name not already in the library); new exercises with the same name are added once; adding to a program stretches its weeks.
- **Education tabs** (`lessons.category`): athlete (athletes, and parents with them), parent (parents: courses and stand-alone reading in the portal's For parents), coach (staff, and published stand-alone ones on the public `/learn` page, never assigned), blog and research (athletes and parents).
